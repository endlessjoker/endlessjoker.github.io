# 列表里的行，凭什么认出自己？

阅读器左边的目录不是一份从头到尾不动的数组。输入筛选词，它会重新挑文件、重新搭树、重新铺平成一行行；定时扫描发现目录变化，也会换一份文件清单。

从 Swift 的角度看，新建的 `LibraryRow` 就是新值。SwiftUI 却还得判断：屏幕上这行《并发笔记》，和刚才那行《并发笔记》，是不是同一行？总不能我在列表前面加一本书，后面的行就集体“转生”。

## 行值重新算，不等于换了身份

当前阅读器给行这样定身份：

```swift
struct LibraryRow: Identifiable {
    var id: URL { node.url }
    let node: LibraryNode
    let depth: Int
}
```

`depth` 是显示时的缩进，`node.title` 是文字，`node.url` 才是这行对应的文件或目录。筛选导致缩进变化、目录重扫重新生成 `LibraryNode`，只要 URL 还是原来那个，同一个 `ForEach` 里的行就有机会被 SwiftUI 认作同一个成员。

注意是“有机会”，不是保证这行的所有内部状态永生。如果筛选词把它完全排除，行就从视图层级消失了；以后再出现，关联的局部 `@State` 不能指望还在。稳定 ID 解决的是**持续出现的成员怎么对应**，不是让已经移除的视图偷偷住进后台。

阅读位置还有更外层的身份。`SavedLibrary.id` 是存下来的 UUID；重新选择已经添加的同一路径时，代码会复用已有的 id，而不是每次打开都换一张身份证。侧栏先 `ForEach(model.libraries)`，再在每个位置里面 `ForEach(model.rows(in: library))`。这两个层级各认各的成员，不能把整张侧栏当成一个没有分组的 URL 数组。

如果文件真的改名或搬家，URL 会变，当前行身份也随之改变。这符合“按文件位置认行”的设计。若以后要做到“搬家后仍把它视为同一本书”，就需要另一个能跨路径变化的文档 ID；单靠现在的 URL 做不到。

## 用下标当 ID，看起来也能跑

一个很容易写出来的替代版，是把铺平的数组带上位置：

```swift
ForEach(Array(rows.enumerated()), id: \.offset) { _, row in
    FolderRow(row: row)
}
```

假如原来有 A、B、C 三行，B 的下标是 1。在最前面插入一本书后，下标 1 变成了 A。SwiftUI 拿到的身份还是 1，却已经不是刚才的成员。

如果 `FolderRow` 自己存着 `@State`，比如一个临时展开标记，这份状态就可能跟着“位置 1”走到另一行，而不是跟着 B 走。动画也可能把插入理解成几行内容轮流变脸。这里不是说我在阅读器里见过这种故障；当前代码用的是 `row.id`，下标版本只是反例。

另一个更直接的坑，是把 `id` 写成每次访问都造新 UUID：

```swift
struct UnstableRow: Identifiable {
    let url: URL
    var id: UUID { UUID() }
}
```

它满足了 `Identifiable` 的类型要求，却没履行“同一个成员下次还叫这个名字”的约定。问两次 ID，可能得到两张不同身份证。`let id = UUID()` 可以用于一份长期保存的模型；但如果每次重建行数据都重新初始化它，问题还是一样。这里能拿 URL 当身份，就没必要摇号。

## 展开状态为什么没放进行里

阅读器现在用 `ReaderModel.expandedFolders` 记录已展开目录的路径。点文件夹时，`toggleFolder(_:)` 增删这份集合，随后还会保存它。行视图只是根据当前集合画箭头，行本身没有一份私有的 `@State isExpanded`。

这正好绕开了筛选时的尴尬：筛选词可能让某个目录行暂时消失；清空筛选后，那行重新出现，模型里的展开路径还在。如果状态只藏在行视图内，即使 URL 作为 ID 很稳定，行离开视图层级后也不能靠它保存这份展开决定。

所以该放哪儿要看状态想活多久。鼠标悬停之类只影响眼前这一行的状态，可以跟着行的视图生命周期。希望筛选、折叠、重扫后仍记得的展开状态，就得放到比行更长寿的地方。第十篇问的是模型活多久，这里只是把同一个问题缩到列表的一行。

## 选中的是哪本，不是第几行

当前侧栏的选择值也没有用数组下标。模型把“哪个阅读位置”和“哪份文件的路径”组合成一个字符串，列表里的文档行用同样的值作 `.tag(...)`。选中值能在重排后继续指向原来的文件，而不是指向新下标上的邻居。

这里有两种用途，别混成一件事：`LibraryRow.id` 帮 `ForEach` 识别动态生成的行；文档行的 `.tag` 对应 `List(selection:)` 里的选择值。它们可以使用不同的类型，只要各自在自己的范围内保持一致。当前选择值带着阅读位置 UUID，正是因为同一份文件可能出现在不同阅读位置的上下文里。

搜索结果也有身份：`BookSearchResult.id` 用阅读位置、文件路径和行号组合。现在的扫描每行只取第一个匹配，所以这一组信息足以区分本轮清单里的结果。若以后改成“一行里每处命中都列出来”，光有行号就不够了，还得加命中的位置；若想让新查询的同一行重新开始局部状态，也要考虑把查询轮次纳入身份。ID 表达的是“什么变化之后仍算同一个成员”，不是随手找个能通过编译的字符串。

写列表时，我现在会先问这个：数据重算以后，哪件东西在业务上还是同一个？阅读位置是保存下来的 UUID，目录行是当前路径，选中项是位置加文件。答案不同，ID 就不该图省事全写成下标。SwiftUI 可以负责比较行；至于谁才算同一行，还是得我先说清楚。
