# 这次到底快没快，不能只靠感觉

假如改完一段读取代码，阅读器打开 Markdown 时转圈似乎短了一点，我很容易顺手写下“性能优化完成”。但换一篇文件、重开一次 App，感觉可能就不一样。文件也许刚好在系统缓存里，WebView 也许已经热起来了。凭一次手感宣布胜利，多少有点像给秒表画了个好看的表盘。

先把“快”说具体。这里最容易记录的是从点开章节到等待遮罩消失，经过了多久。它不等于屏幕像素全部画完的时间，但至少对应着当前界面的一次明确状态变化。另一个问题是等待期间界面能不能响应。还有一个问题是连续切换章节后，内存有没有一直往上长。这三件事可能同时发生，也可能各走各的；只看一个 CPU 百分比，回答不了它们。

## 转圈里装了好几段工作

个人阅读器的 `select(_:)` 会先设置 `isLoading` 和 `isRendering`。后台任务检查文件大小、读取 UTF-8 文本；拿到结果后，`ReaderModel` 在主 actor 上执行 `recordUpdate`，再把文本写进 `markdown` 并更新 `revision`。`ReaderWebView` 看到新 revision，调用网页里的 `renderDocument`。网页发回 `rendered` 消息后，模型才把 `isRendering` 关掉。界面上的等待遮罩由 `isLoading || isRendering` 决定。

所以“从点击到转圈消失”是一段完整的墙上时钟时间。它包括读取、等待任务调度、变化比较、状态更新、向网页传数据和排版，不能拿文件读取的耗时充当整个打开速度。

这里有个容易漏掉的位置：`recordUpdate` 会在旧快照与新文本不同时，按空行拆段、建集合、找增删段落，并更新保存的快照。它是在读文件的后台任务结束**以后**执行的。把 `String(contentsOf:)` 放进 `Task.detached`，并不意味着后面的处理也离开了主 actor。我还没有测出它就是卡顿来源；只是按代码看，它值得单独量一次。

我会给这段工作临时加一个 Instruments 能识别的区间，类似这样：

```swift
import os

private let documentSignposter =
    OSSignposter(subsystem: "ReaderNotes", category: "Document")

// select(_:) 读取成功后，暂时包住原有调用
let interval = documentSignposter.beginInterval("RecordUpdate")
recordUpdate(text, url: url)
documentSignposter.endInterval("RecordUpdate", interval)
```

这只是准备加的测量代码，不在当前阅读器里。它量到的是 `recordUpdate` 整次调用，包括段落比较和快照存取；名字不能写成“CompareParagraphs”然后暗示两者相等。再给打开动作和收到 `rendered` 消息各留一个时间点，就能把总等待与其中一段对齐。若这一段很短，继续盯着它优化就有点冤枉它了。

## 等得久，不一定是主线程卡住

假设遮罩转了两秒，期间窗口、侧栏、按钮都能响应。这是**等待长**，还不能叫主线程卡死。可能是文件读取慢，也可能是网页排版还没回消息。反过来，如果滚动和按钮都停顿，即使遮罩很快消失，也应该看主线程在那一刻做了什么。

区间标记给我的是开始到结束的实际经过时间；它本身不告诉我 CPU 在谁身上烧掉。Time Profiler 才适合看采样时哪些函数占了处理时间。主线程若在忙，调用栈可能指出是模型计算、视图更新还是别的同步工作；若它在等，线程状态比猜一段 Swift 代码更有用。

SwiftUI 的更新也得放在自己的位置看。`revision` 变化会触发视图更新，`NSViewRepresentable` 的 Coordinator 又会把新正文交给 `WKWebView`。SwiftUI 的 `body` 算得频繁，和网页排版费时，是两个不同问题。看到 SwiftUI 视图更新次数多，不能直接推出 `renderDocument` 慢；看到网页慢，也不能反过来说 `body` 一定没问题。先看卡顿落在哪段，再决定看 SwiftUI 的视图更新轨迹，还是看 WebView 那侧的工作。

目录扫描和全文搜索也有各自的入口。目录扫描更新 `libraryChapters`，全文搜索逐本读文件；它们若与打开章节同时发生，单次总耗时就混入了别的工作。我会保留一组只打开同一篇文档的记录，再单独观察扫描或搜索期间打开它的记录。否则优化前关着搜索、优化后刚好开着搜索，比较出来的数字只是在考验运气。

## 内存往上走，先看留下了什么

打开大文件时，内存到一个高点不奇怪：文本、变化快照、传给网页的内容、网页排版，都可能暂时占空间。关键是反复切换、关闭阅读窗格之后，有哪些对象或数据仍被持有，数量是否持续增加。

这里不能把进程内存曲线没有立刻降回起点，就判成泄漏。分配器和系统缓存可能暂时保留已申请的内存。Allocations 里按时间看分配与存活对象，内存图里看意外持有关系，比盯着一个总数更接近问题。比如某个 `WKWebView` 或 Coordinator 在窗格销毁后仍有实例留着，就要沿引用链查；如果是 `libraryChapters` 随着添加阅读位置增长，那是模型有意保存的目录，问题变成预算和使用场景，而不是一个 `weak` 能解决的泄漏。

前面那篇缓存笔记讨论过的变化快照有单篇大小和篇数上限；这不等于整个 App 的内存上限。当前正文 `markdown`、目录索引、网页自己的占用都不在那笔账里。给未来的正文缓存写一个“最多八 MB”，也只能约束那层缓存记的成本。真正用了多少内存，最后仍要看进程的实际分配和存活情况。

## 同一问题，至少拿同一组条件比

我会记下文件、文件大小、App 构建版本、是否首次打开这篇文档，以及从点击到 `rendered` 的时间，再看几次相近条件下的结果。首次打开和已经打开过一次的情况分开记；不要拿两种情况直接比，然后宣布某行代码救了世界。更改前后的文件、操作和测量点也要相同，不然那个“快了”连自己都解释不清。

如果总等待缩短，`RecordUpdate` 区间却没变，改进大概不在段落比较里；如果主线程停顿消失，但总等待没变，打开正文仍要等，却至少可以继续操作；如果响应和等待都改善，内存却随着切换一直涨，也不能就此收工。这些判断比一个孤零零的性能等级更具体，且能指向下一步该查哪段。

写这十八篇时，很多看起来顺手的改动最后都变成了同一个问题：我到底知道代码在做什么，还是只觉得它应该如此？性能这件事尤其不给面子。先给等待、卡顿和存活对象各找一个能观察的位置，再动代码。等阅读器真跑出数字，才有资格说这次快了。
