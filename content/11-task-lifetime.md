# 页面关了，任务怎么还在跑？

搜索页关了，输入框不见了。搜索任务是不是也该停？

第十篇把模型留在父页面，是为了记住上次的词和结果。这样一来，sheet 消失时，模型还活着，里面那份任务也不会仅凭“页面没了”就自动收到取消信号。

这不是我在阅读器里复现过的一次故障。顺着现在的代码，就能看出这个生命周期问题。

## 现在这份任务跟谁走

当前搜索页在出现时调用 `model.searchBooks()`，输入变化时也调用它。`searchBooks()` 把新建的任务放在 `ReaderModel.fullSearchTask` 里，下一轮搜索开始前会取消上一轮。

但搜索页关闭时，没有相应的 `onDisappear` 取消处理。`ReaderModel` 是应用入口持有的对象，sheet 关了，它并不会跟着结束。模型结束时虽会取消 `fullSearchTask`，那也不是“刚关搜索页”这个时机。

所以如果我输入一个词，扫描正好开始，然后关掉弹窗，这一轮工作仍可能继续。它完成后，模型里的结果也可能更新，只是这时没开着搜索页看它。

有时这反而是想要的：关掉页面，搜索在后台做完，下次打开直接看结果。也可能是在白读一堆教材。要选哪种行为，得由产品决定，SwiftUI 不会根据弹窗的标题猜。

这里我更想保留上次的输入和已经显示的结果，关闭时停掉尚未完成的搜索。下次打开再用同一个词搜一次，也照顾到文件在此期间改过的情况。

## 取消任务，不用顺手清空输入框

沿用第九篇拟议的 `SearchModel`，给它一个专门的入口：

```swift
extension SearchModel {
    func pause() {
        task?.cancel()
        task = nil

        if let batch = state.displayedBatch {
            state = .finished(batch)
        } else {
            state = .idle
        }
    }
}
```

这段 extension 要和 `SearchModel` 放在同一个 Swift 文件里，才能访问它的 `private` 属性。

这里没有改 `query`。输入了 `Task`，关掉再打开，还是 `Task`。

如果新搜索期间显示着上一轮 `actor` 的结果，`displayedBatch` 仍是 `actor` 那批。暂停后把状态改成 `.finished(batch)`，它不会突然冒充 `Task` 的新结果。下次出现时调用 `update`，再按输入框里的 `Task` 发起请求。

第一次搜索还没有旧结果，暂停就回到 `.idle`。这个状态说的是当前没有一份可展示的已完成搜索；输入框里仍然可以留着词。第七篇已经把输入和搜索进度分开，这里正好用上。

`task = nil` 只是把模型持有的任务句柄放下，真正发出取消信号的是前一行的 `cancel()`。顺序倒过来，连要取消哪份任务都找不到了。

关闭后又出现新一轮搜索时，旧任务回来的检查也要留着。上篇的模型同时检查取消状态和请求编号；暂停把状态换走后，旧编号也不再是当前待完成请求。旧任务即使交回报告，也不能替新页面宣布完成。

这个 `pause()` 重复调用也能保持同样结果：没有任务可取消就跳过，已经保存的旧 batch 还是那份。按钮和页面消失的回调有时都可能走到这里，不必靠“它们绝不会同时发生”维持正确性。

## 页面消失时，通知模型

展示 sheet 的地方可以接上：

```swift
SearchEditor(model: search, sources: sources)
    .onAppear { search.update(sources: sources) }
    .onDisappear { search.pause() }
```

关闭弹窗后，父页面还保存着 `search`；`onDisappear` 只通知它停下当前工作。按钮主动关闭、系统方式关闭，最终都可以走页面消失这条路。要让“完成”按钮一按就尽快停，也可以在按钮动作里先调用 `pause()`，再请求关闭。

这里说的是第十篇那个父页面持有模型的改法。当前阅读器还没有这个 `pause()`，也没有给全文搜索页加这段消失回调。

`onDisappear` 也不是一张“后台已经全部结束”的收据。它调用取消后，可能仍有一次同步文件读取正在执行。取消信号会转给 detached worker，但同步读取不因此立刻中断；worker 要到能检查取消的位置才会停。

如果下一步要立即释放书签授权、移除目录，就不能只看见 `pause()` 返回便认定没人再用文件。第三篇留下的授权与在途读取问题，在这里仍然成立。

## SwiftUI 的 task 是另一种归属

SwiftUI 还有 `.task`。附在视图上的任务，其生命周期由 SwiftUI 按视图身份管理；视图离开后，SwiftUI 会取消尚未完成的任务。`.task(id:)` 的 `id` 变化时，还会取消旧任务并重新开始。

不过把现有方法塞进去，不能直接拿到这种效果：

```swift
Text("全文搜索")
    .task(id: model.query) {
        model.update(sources: sources)
    }
```

`update` 自己创建一份 `Task`，保存到模型，随后就返回。SwiftUI 管理的是 `.task` 闭包那份任务；它很快结束了。真正等待 300 毫秒、扫描文件的是模型后来保存的另一份任务。

输入改变时，`update` 会自己取消上一次搜索；但页面消失时，不能因此认定模型保存的任务也被 SwiftUI 自动取消。任务写在 `.task` 的大括号里，不等于它变成了 SwiftUI 那份任务的结构化子任务。

要让 SwiftUI 的视图任务真正负责搜索，就得让异步搜索过程留在它所等待的调用链中，并把取消一路传到实际扫描。那是另一种设计，不能只把 `.onAppear` 换成 `.task` 这几个字就算完成。

我现在选的是模型持有任务、界面通知模型暂停。搜索词和旧结果要跨弹窗保存，这个分工比较直观。

## 三份工作，取消信号要接三次

把一路上的任务摆出来，关系就清楚了：

| 任务 | 谁管理它 | 收到取消以后 |
|---|---|---|
| SwiftUI `.task` | SwiftUI 按视图身份管理 | 取消视图任务；不会自动替另行创建的模型任务收尾。 |
| `SearchModel.task` | 模型保存句柄，`update` 或 `pause` 取消 | 通过取消处理通知 worker，等待返回后拒绝过期回写。 |
| detached worker | 执行文件读取和匹配 | 检查取消后退出；正在进行的同步读取要先返回。 |

这个表里第二行的“通知 worker”，靠的是第九篇 `searchOnDisk` 里的 `withTaskCancellationHandler`。拿掉它，外层 `cancel()` 依然能阻止结果回写，却不能据此说磁盘扫描也收到取消。

第三行也不是立即终止线程。文件之间、逐行匹配时能检查；读取一个文件或拆分整篇正文那段同步工作，还是有自己的耗时。

`Task.isCancelled` 检查的总是当前执行代码所属的任务。worker 查自己的标记，模型回写前查外面那份的标记。别拿模型属性里的最新句柄，替正在返回的旧任务决定去留；第三篇已经踩过这个逻辑坑。

## 任务活得久，也未必是错

搜索页关闭就暂停，适合我现在想要的交互。换成下载一份教材，关掉进度弹窗不一定意味着下载应该停；任务可能属于整个阅读窗口，甚至应用里的下载管理器。

判断依据是工作由谁发起、结果给谁用、关闭哪个界面才算不需要。先弄清楚所有者，再选 `.task`、模型句柄或更长寿命的服务。光看代码摆在哪个 `View` 文件里，不够。

第十篇解决了“这份模型该由谁保存”，这一篇补上“这轮工作该由谁结束”。再往后，模型属性一改，哪些 SwiftUI 视图会更新？第十二篇就从搜索状态的读取位置继续看。
