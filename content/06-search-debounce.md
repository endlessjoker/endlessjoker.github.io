# 字还没打完，先别把整本书搜一遍

阅读器能打开好几个教材目录以后，光按文件名筛选就不太够了。有时候记得书里讲过某个方法，至于藏在哪一章，完全没印象。

于是又加了全文搜索。输入一个词，把已经添加的 Markdown 文件找一遍，列出文件名、行号和附近的文字，点一下跳过去。

听着还是个小功能。只是输入框里的词会一直变，磁盘上的书可不会跟着变少。我要输入 `actor`，程序要是从 `a` 开始就认真扫书，勤快得有点让人不好意思。

## 先看搜索是怎么开始的

界面里这两行，把输入和搜索接在一起：

```swift
TextField("搜索所有已添加位置的正文", text: $model.fullQuery)
    .onChange(of: model.fullQuery) { model.searchBooks() }
```

输入更新 `fullQuery`，SwiftUI 响应它的变化，再调用 `searchBooks()`。搜索窗口刚出现时，也会调用一次，处理之前留在输入框里的词。

不过调用这个方法，不等于马上开始读文件。方法开头先处理旧任务和空输入：

```swift
fullSearchTask?.cancel()

let query = fullQuery.trimmingCharacters(in: .whitespacesAndNewlines)
guard !query.isEmpty else {
    fullResults = []
    searching = false
    return
}
```

取消放在空值检查前面，这个顺序有用。清空输入框时，旧搜索也得作废，不能只把列表清空，等旧任务回来又把它填上。

去掉首尾空白之后，如果已经没内容，就不往下创建任务了。输入了一串空格，总不至于也值得把教材读一遍。

## 只加等待，会变成晚一点再白忙

非空输入会创建新的 `fullSearchTask`。开始扫描前，先经过这两行：

```swift
try? await Task.sleep(for: .milliseconds(300))
guard !Task.isCancelled else { return }
```

前一句让这份任务先等一等，后一句决定醒来后还要不要干活。

如果我在这 300 毫秒里继续输入，下次 `searchBooks()` 会取消旧任务，再创建一份新的，重新等 300 毫秒。

不计任务调度的延迟，连续输入大致会是这样：

```text
  0 ms：输入 a      → 开始等待
100 ms：输入 ac     → 取消上一轮，重新等待
220 ms：输入 actor  → 再取消上一轮，重新等待
520 ms 左右        → 这轮还有效，开始扫描
```

这就是这里的防抖：输入变化得太密，就先不开始昂贵的搜索，等停下来一小会儿再处理最后那份。

如果只是每轮都睡 300 毫秒，却不取消旧任务，`a`、`ac`、`actor` 仍然各搜一次，只是一起晚点开工。工作量一点没少，还容易造成一种“都异步了，怎么还这么忙”的错觉。

`Task.sleep` 也没有让主线程睡觉。等的是任务，输入框还能接着输入。它更不保证 300 毫秒以后结果就出来了，后面还有读文件和匹配的时间。

而那个取消检查，接着第五篇的 `try?` 问题：睡眠被取消会抛错，`try?` 忽略错误后，代码仍会继续。只有把取消状态也检查了，已经作废的输入才不会趁着“提前醒来”立刻启动扫描。

## 这次究竟搜什么，出发前先拿好

前面已经把输入存进局部的 `query`。模型还会把待搜索的文件整理出来：

```swift
let sources = libraryChapters.flatMap { id, chapters in
    chapters.map { (id, $0.url) }
}
```

`libraryChapters` 是模型管理的各个阅读位置及其文件列表。这里把它们变成一组“阅读位置 ID + 文件 URL”。

`query` 和 `sources` 都在创建任务前取得。这一轮任务拿着这些值去工作，不需要读一个文件，就回头问模型一次“输入框现在写的是什么”。

不然同一轮扫描就可能前半本按旧词查，后半本按新词查。结果倒是很多，就是不知道搜了个什么。

后台扫描用的是 `Task.detached`。它读取这些输入，在自己的局部数组里收集结果；模型中的 `fullResults` 则等扫描返回后再更新。这里没有让后台任务直接往界面正在使用的数组里一条条追加。

每一条结果是这样的值：

```swift
struct BookSearchResult: Identifiable, Sendable {
    var id: String { library.uuidString + url.path + String(line) }
    let library: UUID
    let url: URL
    let line: Int
    let snippet: String
}
```

这些字段分别记着阅读位置、文件、行号和摘要。`Identifiable` 供列表区分条目；`Sendable` 表明这种值可以安全地跨并发隔离传递，由编译器检查相应要求。

它没有因为标了 `Sendable` 就自己跑到后台，也没有获得一把自动锁。这里能传过去，是因为组成结果的数据本身适合这样传递。随便把一个装着共享可变对象的 struct 加上这个名字，事情不会就此解决。

还有一层区别：提前拿到的是 URL 列表，不是文件内容的冻结副本。扫描期间，磁盘上的文件仍可能被修改、移走或者读不到。保存了这份列表，不等于顺便保存了当时的整个文件系统。

## 文件已经读上了，再输入怎么办

防抖能省掉尚未开始的扫描，却挡不住这种情况：我停顿了一会儿，搜索已经开始，然后又多打了一个字。

这时取消外层任务，还得通知里面真正干活的 `worker`：

```swift
let results = await withTaskCancellationHandler {
    await worker.value
} onCancel: {
    worker.cancel()
}

guard !Task.isCancelled else { return }
fullResults = results
searching = false
```

外层被取消，`onCancel` 就把信号转给后台任务。扫描文件的循环里有 `Task.isCancelled` 检查，发现取消就退出。

但当前检查放在文件之间。一次已经开始的同步读取，或者当前文件里还在进行的逐行匹配，并不会被强行掐断。下一轮搜索开始时，上一轮可能还在收尾，不能据此认定后台永远只有一份扫描在运行。

这也说明为什么回来以后还要再检查一次取消。worker 提前退出，可能交回已经找到的一部分结果；如果外层已经过期，这些结果照样不能替换当前列表。

两道检查各自守着一个时机：等待输入之后，决定是否值得开始；等待扫描之后，决定这批结果是否还允许显示。

`searching = false` 也留在最后这道检查后面。旧任务结束，不意味着新任务已经结束。旧任务如果抢着把转圈关了，新搜索就会看起来像根本没在运行。

`onCancel` 里只调用 `worker.cancel()`，没有去清空列表或改加载状态。取消处理可能和正在进行的工作并发发生，本来就不适合在这里直接修改 MainActor 管理的界面状态；再说，状态现在也未必还归旧任务管。

外层等待结束后回到 MainActor，检查与这两次赋值之间没有新的 `await`，因此新一轮搜索不会插进这几行的中间。这和第三篇加载正文的道理接上了，只是现在多了一段“先别急着做”的等待。

## 结果没串台，点开的时候却可能串台

顺着界面继续看，还能找到一个单靠取消解决不了的问题。

现在开始非空搜索时，会把 `searching` 设成 `true`，但不会清空之前的 `fullResults`。新结果出来前，列表仍然显示上一轮内容，而且按钮还能点。

保留旧内容并不奇怪。每输入一个字就把列表清空，界面也挺折腾的。只是这些旧结果仍然属于旧的搜索词。

当前打开结果的方法是：

```swift
func openResult(_ result: BookSearchResult) {
    search = fullQuery
    activate(result.library, document: result.url)
    pendingFind = fullQuery
    searchResultLine = result.line
}
```

它拿条目里的文件和行号，却拿输入框当前的 `fullQuery` 做后续查找。

于是有这样一种可能：列表还是搜 `actor` 得到的，我已经把输入改成 `Task`，新搜索尚未完成，就点了旧条目。打开的是旧结果对应的章节和行号，准备高亮的却是新词。

这次没有旧任务回写，也不需要两条线程同时修改任何东西。信息本身就来自两轮搜索，MainActor 再认真排队，也管不了这个。

如果继续完善，我会让显示中的这批结果带着它实际使用的查询词。点击时用这份词，而不是临时去读输入框。搜索前去掉的首尾空白也能一起保留下来，免得扫描用的是处理过的词，高亮时又换回原样。

另一种更简单的选择，是新搜索期间暂时不让旧条目被点击。无论选哪种，都得承认“正在输入的词”和“当前这批结果对应的词”可能不同。现在的代码还没有把这层关系表达出来。

## 搜完了，也不一定是把所有书都搜完了

当前搜索有两个明确的上限：单个文件超过 2 MB 就跳过，结果达到 300 条就返回。界面已经把这两个限制写出来了。

它按行找包含查询词的位置，每个命中的行生成一条结果，再截取附近文字作为摘要。所以同一行出现好几次，不会因此产生好几条结果；300 条也不是按相关性挑出的“最佳 300 条”，只是扫描中先收集到的那些。

文件大小读取失败、正文读取失败，也会直接跳过该文件。于是零条结果可能是没有匹配，也可能有些文件根本没参与搜索。后面如果需要更完整的提示，就得把跳过和失败的信息也带回来，不能只有一个结果数组。

这样看，搜索框后面要保存的已经不只是一个词、一组结果和一个转圈了。输入在变，旧结果还在显示，新任务也许正在等待或扫描。

下一篇想把这几个状态整理一下。否则模型里的属性各自看着都合理，组合起来是不是同一轮事情，还得靠脑子帮它们记账。
